# 08 · 会话复用与任务连续性：可行性规划

> 结论先给：
> **① 复用被派发的会话——可行，但它打破「一任务一会话」的隐含假设，是结构性改造，不是加一个参数。**
> **② 让插件自动判断「这两个任务连不连续」——不建议。** 改为「显式续派 + 候选建议 + 硬校验」。
> **③ 顺序：先做 07 的 P0（记忆治理），再做复用。** 复用是上下文污染的放大器，先治理再复用。
> 依据：本仓库 `src/**`（0.8.x 未发布）、`plans/07-memory-governance.md`、`plans/00-vision.md` §4 的产品口径。

---

## 一、先说清楚：一半已经有了

| 场景 | 现状 |
|---|---|
| 同一个任务还要接着干 | **已支持**：`dispatch_message` 会把任务重新拉回 `running`，消息塞进**同一个** worker 会话，历史保留 |
| 新任务、但属于同一条工作线 | **没有**：`dispatch_launch` 一律 `dispatch-<taskId>` 新开会话，历史断掉 |

所以真正缺的不是「续跑」，是「**新任务复用旧会话**」。这两件事的成本差一个数量级，必须先分清。

---

## 二、两种可选模型

### 模型 A：同任务续派（零结构改造）

`dispatch_launch({ continue_task_id })` 内部转成对该任务的 `dispatch_message`，只追加一条新要求。

- 优点：**今天就能做**，不改任何数据结构；
- 代价：没有独立的任务记录、独立的报告链、独立的看板行；「这次要求」和「上次要求」混在同一个任务里；
- 适用：用户只是"再补一句"，不关心任务粒度。

### 模型 B：同会话多任务（thread 模型）

新任务照常建记录（标题、简报、报告、状态都独立），但 `workerSessionId` 指向已有会话，任务带 `parentTaskId` 形成一条线程。

- 优点：保留任务粒度，报告/取消/统计都能分开；会话复用真正成立；
- 代价：**必须打破 1:1 假设**（见 §三），是一次结构性改造；
- 适用：一条工作线被拆成多个任务（如"先改接口，再补测试"）。

| 维度 | 模型 A | 模型 B |
|---|---|---|
| 改动面 | 一个参数 + 转发 | 任务表、归属查询、取消、归档、看板、并发口径 |
| 任务粒度 | 丢失 | 保留 |
| 报告归属 | 天然正确 | 需要显式绑定 |
| 并发 | 天然串行 | 同会话只能串行，需排队 |
| 取消 | 取消整个会话回合 | 必须能只取消其中一个任务 |
| 归档 | 按会话 | 必须按线程 |

---

## 三、可行性硬点（都是代码里的事实）

1. **`TaskTable.byWorker(sessionId)` 返回第一个匹配的任务**。
   两个任务共享会话后，`dispatch_report`、`agent/status → idle`、`agent/disposed`、读回执全会指到**最早那条任务**上。
   → 必须先有「会话 → 当前活跃任务」的显式绑定，否则功能一上线就串账。
2. **`archiveStale()` 按任务的 `workerSessionId` 归档会话**。
   归档其中一条任务 = 把整条线程的会话收走，其它任务全部受影响。
3. **`cancel()` 取消的是会话当前回合**。
   共享会话时，「取消任务 A」会打断正在跑的任务 B。要么明确拒绝（同会话有别的活跃任务时不可取消），要么做任务级中断（成本高）。
4. **模型 / preset / 权限在会话创建时定死**（`applyModel` 只在首个请求前生效）。
   复用 = 沿用旧模型；新任务想要更强的模型，只能新开会话。
5. **工作区与 cwd 绑在会话上**（`createWorker` + `enterDirectory`）。
   跨工作区复用必须**拒绝**，否则任务 A 的代码会被任务 B 改。
6. **并发位按任务计**（`runningCount()`），而一个会话同一时刻只能跑一个回合。
   同会话的两个任务必须排队，否则并发数字虚高、实际串行。

> 一句话：模型 B 不是"加个 if"，是先把「会话 = 任务」改成「会话 = 线程，任务 = 线程上的一段」。

---

## 四、连续性怎么判：不做自动判定

**插件不该自己判断两个任务是不是一回事**，三条理由：

1. **它没有语义**。插件只看得到标题、简报、工作区、时间，看不到代码、上下文和你的意图；
2. **误判代价不对称**。判错"连续"→ 新任务被塞进旧上下文，带着旧结论、旧错误、旧分支，还改不了模型；判错"不连续"→ 只是多开一个会话，代价小得多；
3. **与本仓库既有口径一致**：`plans/00-vision.md` §4 已经定过「工作区识别交给 agent，插件只负责解析和校验」。连续性判定是同一类问题。

替代方案：**显式续派 + 候选建议 + 硬校验**。

- **显式**：`dispatch_launch({ continue_from: <task_id | session_id | thread_id> })`；不传就是新线程。
- **建议**：`dispatch_launch` / `dispatch_sessions` 只读地返回候选——同工作区、已结算、最近 N 天、标题与摘要关键词重合（**只用于排序和提示，不自动绑定**）。
- **硬校验（四条，缺一即拒绝并说明原因）**：
  1. 目标会话存在且是本插件建的（`dispatch-*`）；
  2. 工作区 / cwd 一致；
  3. 未归档、未退休；
  4. 当前没有别的活跃任务（或明确允许排队）。
- **逃生门**：任何一次复用都可显式选择"另起会话"，不需要先解释理由。

## 五、与记忆治理（07）的关系

这是两份规划必须一起看的地方：

| 交互 | 结论 |
|---|---|
| 复用放大污染 | 每次复用都会把前序全部历史带进新任务。**所以复用必须配「交接摘要」**：上一任务终态 + 未决问题 + 变更面 + 这次目标，而不是把历史整个搬过去 |
| 线程级生命周期 | 「何时退休一整条线程」应并入 07 的 G4（退役冻结），否则线程会无限长 |
| 指标口径 | 07 的 P0-1 要把「按任务」和「按线程」两个口径分开，否则复用率高的用户看到的中位耗时会被摊薄 |
| 07 的 P1-2（事实/投影分离） | 是复用的前置红利：正文留在账本、会话只收摘要，复用才不会一次带进几万字 |

**顺序建议**：07 的 P0（指标窗口、准入分级、单条预算、生命周期、封顶）先落地，再做复用。
理由很直接：治理没做就复用，等于把「已经会污染的东西」复制 N 份。

## 六、分期

| 阶段 | 做什么 | 为什么这个顺序 |
|---|---|---|
| 0 · 解耦 | 把「会话 ↔ 任务」从隐式 1:1 改成显式绑定（`activeTaskId` + `task.threadId`）；行为完全不变，测试全绿 | 归属错乱是最高风险，必须单独一步、可回退 |
| 1 · 最小可用 | 模型 A：`dispatch_launch({ continue_task_id })` 转发为续派；看板已结算行加「续派」按钮 | 零结构改造，先验证「连续性」是不是真需求 |
| 2 · 线程模型 | 模型 B：新任务复用会话 + 交接摘要 + `parentTaskId`；看板显示线程 | 需要阶段 0 与 07 P0 都就位 |
| 3 · 线程生命周期 | 线程级归档/退休，与 07 合流 | 没有 3，线程会变成新的容量黑洞 |

**不做**：自动语义判定、跨工作区复用、复用中改模型/preset、跨批次（`group`）复用——前三个是正确性问题，最后一个是统计口径问题。

## 七、验收（可观测信号）

1. **归属正确**：同一会话上有两个任务时，`dispatch_report` 记到正确任务上（构造并发用例，串账即为失败）。
2. **取消隔离**：取消 A 不会让 B 变成 `interrupted`；做不到就明确拒绝并给原因。
3. **归档安全**：归档一条任务不会让同线程其它任务不可用。
4. **首条消息**：复用任务收到的是「交接摘要 + 本次目标」，不是完整 `workerPrompt`，且长度有上限。
5. **线程预算**：复用 5 次后，单会话的插件来源消息条数仍在线程预算内（配合 07 的验收第 1 条）。
6. **可回滚**：`reuseSessions: false` 时行为与今天完全一致（默认关）。
7. **统计不串**：看板的并发、成功率、复用率按「任务 / 线程」两个口径分别可查。

---

## 八、风险与对策

| 风险 | 对策 |
|---|---|
| 归属错乱（最高） | 阶段 0 先做显式绑定；上线前用"同会话两任务"用例把 report / idle / cancel / 归档全打一遍 |
| 上下文污染与陈旧假设 | 交接摘要 + 线程预算 + 随时可另起会话 |
| 取消语义模糊 | 同会话有活跃任务时，取消返回 409 并说明；不做静默打断 |
| 模型不可换 | UI 与工具都写明"复用沿用原模型"；要换模型只能新开 |
| 归档拆线程 | 归档语义改为线程级；单任务归档只标记，不归档会话 |
| 需求是伪需求 | 阶段 1 先跑两周，看「续派率」；低于预期就不做模型 B |

---

## 九、一句话总结

- **复用会话：能做，但要先付"解耦 1:1"的账**；不做这一步，功能上线必串账。
- **自动判断连续性：不做**；给模型和用户「显式续派 + 候选建议 + 四条硬校验」。
- **先治理记忆（07 P0），再复用（08 阶段 0/1）**；模型 B 单独一版，且默认关闭。
