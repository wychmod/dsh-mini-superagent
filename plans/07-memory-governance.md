# 07 · 派发记忆治理（memory governance）规划

> 结论：**要做，但不是"再加一个记忆库"**。要加的是一条关于「哪些事实是权威、哪些只是投影、何时合并、何时退休」的**治理策略**。
> 本文只定「是什么 / 要不要 / 做到什么算做到」，不展开实现。
> 依据来自本仓库 `dsh-mini-superagent/src/**`（0.8.x 未发布）、`docs/api-contracts.md`（编译产物取证）、
> `reference/dsh-superagent-prototype`（上游同宿主实现）。

---

## 一、一页结论

| 问题 | 回答 |
|---|---|
| 需要新能力吗 | **需要**。现在没有任何组件对「派发产生的事实」负责生命周期 |
| 它是什么 | 「写入前 + 投影前」的闸门：准入、合并、退役、封顶。**不是**第二个存储、不是向量库、不是给模型加记忆工具 |
| 它不是什么 | 不是新 `ctx.<key>` 服务，不改 Session 格式代际，不碰 agent loop，不给用户加一堆旋钮 |
| 为什么现在做 | 五类问题里四类已在代码里可复现，且随使用时长**单调恶化**（没有回收路径） |
| 什么时候不用 | 一次性 headless 派发、短任务、任务总量长期很小、`tasks.json` 只当审计不参与判断 |
| 首期范围 | P0 五项：指标窗口、准入分级、单条消息预算、生命周期清理、账本封顶。不改状态机 |

---

## 二、现状：五个问题的证据

### 1. 记忆混淆（高）

报告以 `user/message` 写进主会话，`source.kind='dsh-mini-superagent'` 只是**来源标签**，模型看到的是纯文本。
`sessions.deliver()` 的降级路径（收件箱不可用 → `sessionController.prompt`）会把来源退化成 `kind:'user'`，
代码注释自己写着「主会话会把它当成用户消息」。批次汇总、idle 兜底、后台结束通知混在同一条流里，
**没有「事实」与「指令」的区分**。

### 2. 上下文污染（中高，随时长线性增长）

- 每任务最多 `MAX_REPORTS = 50` 条报告；单条 `summary` 外发时截到 6000 字、`detail` 4000 字；
- `progress` 已按 `progressRelayIntervalMs = 60s` 节流，但终态、失败原因、批次汇总、idle 兜底仍持续回流；
- `inject` / `steer` / `followup` 三条路径最终都落进会话事件日志；
- 宿主的 `tool-result-pruner` 裁的是**工具结果**，插件来源的 `user/message` 不在其列——这一类污染压缩兜不住。
  `tasks.js` 的 `clip()` 注释已经承认「会把消息撑出上下文预算」。

### 3. 信息覆盖（中，多为有意但无留痕）

`reports.splice` 丢第 51 条起、`delivery` 只留最后一次、`error` 每次覆盖、`lastText` / `background` 单值、
`targets` 按 sessionId 覆盖。有界覆盖是防膨胀的设计，问题是**覆盖前不留痕**：
报告没送到被后一次覆盖后无从追查。上游反而保留（"a dropped message keeps its record, with when and why"）。

### 4. 过期内容残留（中高，最被低估）

- 归档只打 `archivedAt` 并归档子会话，**任务记录永不删除**；
- `agent/disposed` 只清 routers / subagents 并结算任务，**不清 `targets`**（只有 `setTarget('')` 才删）；
- `inputPendingAt` 在宿主不发 `session/event` 时永久挂「待读」；
- **派生指标吃全历史**：看板的成功率、中位耗时、并行节省由 `effectStats()` 对全部未归档已结算任务计算，
  上个月失败的任务仍在给今天的数字投票。

### 5. 容量膨胀（中，长会话显著）

- 没有全局任务表上限：`maxTasksPerSession = 64` 只数**未收尾**任务（`quotaUsed()`，已结算超 24h 与已归档不计）；
- **报告正文入库不截断**：`report()` 直接把 `summary` / `detail` 原样推进 `task.reports`，
  只有外发时才 `clip`。所以单任务体积实际由调用方决定，没有硬界；
- brief 落盘上限 `max(2000, maxBriefChars×2)` = 24000 字，每任务还带 `lastText`；
- 写盘是 800ms 防抖的**整表覆盖**（`JSON.stringify` 全量 → fsync → 备份 → rename），膨胀同时带来写放大；
- 看板 `MAX_TASKS = 200` 只截显示，`counts` 仍按全量算（注释里就举了「总计 500 / 列表 200」的例子）。

> 最坏情况的数量级：单任务 50 条 × 1 万字 ≈ 50 万字，1000 条任务就是数亿字符的 JSON。
> 实际报告远短于此，但**没有上限就是没有上限**。

### 一个口径冲突（文档说 vs 代码是）

`store.js` 注释与 README 都说状态文件是「辅助信息，丢了不影响子会话」；
但看板指标、任务归属、续跑、`dispatch_inspect` 全读这份表，而会话里的报告一旦写入不可回收。
**事实上的权威源已经分裂成两份**，谁都不是唯一权威——这才是「混淆」的根，不是「长期和短期放一起」本身。

## 三、能力定义：四个概念

1. **权威事实（source of truth）**：跨任务事实只在账本里有一份权威副本。
2. **投影（projection）**：会话里的一切都是可重建的投影，不得反过来成为事实。
3. **生命周期（lifecycle）**：每条事实有明确阶段——活跃 → 结算冻结 → 归档只读 → 退休留痕。
4. **预算（budget）**：账本有总量上限，会话有"每次注入多少"的上限。

四个概念落到一条规则上：**先定权威，再定投影，然后给生命周期和预算**。顺序反了就会变成"删历史"或"藏数据"。

---

## 四、管理目标与预期行为

| # | 目标 | 预期行为（可观察） |
|---|---|---|
| G1 | 单一权威 | 任一事实能从账本重建；会话里没有"只存在于消息、不在账本"的事实 |
| G2 | 写入准入 | 只让「终态 / 需要人处理 / 答问 / 批次汇总」进会话长期历史；进度、状态变更只入库 |
| G3 | 合并去重 | 同任务同 key 的未消费通知合并为最后一条；重试与兜底不产生重复条目 |
| G4 | 退役冻结 | 结算即冻结、归档即只读；退休记录带「何时、为什么」，仍可查询但不参与当前指标 |
| G5 | 预算封顶 | 账本有全局上限；会话每回合的注入量有上限；到界按规则退休最老的非活跃记录 |

## 五、边界

**需要**：默认主会话常驻并被当项目记忆复用几天；多批次 / 多工作区并行；反复 `dispatch_message` 续跑；
长时间后台活；`reportOnTurnEnd` 常开；拿看板效果数字做判断。一句话：**任何把历史任务事实喂回模型决策的用法**。

**不需要**：一次性 headless（进程结束即丢）、短任务、任务总量长期 < 数十、把账本当纯审计。

**硬约束（决定能做什么）**：

- **模型可见即已记录**：治理不能删事件、改历史消息，只能作用于「写入前」与「投影前」；
- **已发布的 Session 格式代际不可变**（本机看到的是 `session.v4.jsonl.zstd`），不能为了治理改消息形状；
- **scope 只有两层且不继承给 subagent**：per-worker 的预算只能靠 lineage 表达，不能靠作用域继承；
- 不碰 agent loop（仓库最敏感区域）；不新增会话事件类型；不引入新服务键。

## 六、分期

### P0 · 止血（不改状态机、不动 Session 格式、不改工具契约）

| 项 | 做什么 | 为什么先做 |
|---|---|---|
| P0-1 指标窗口化 | 效果数字改成「最近 N 天 / 最近 M 条已结算」并显示窗口；归档任务彻底移出 | 旧事实污染当下判断，改动最小、收益最直观 |
| P0-2 准入分级 | 明确「必须直通」：`blocked` / `failed` / 提问 / 批次汇总；其余只入库 | 混淆与污染的主要来源 |
| P0-3 单条消息预算 | 报告入库就截断并标 `truncated`（现在只有外发才截） | 无硬界是容量膨胀的根之一 |
| P0-4 生命周期清理 | 会话关闭清 `targets`；`inputPendingAt` 设 TTL（超时标 unknown）；归档打 `retiredAt` | 残留最容易被忽略，且几乎零风险 |
| P0-5 账本封顶 | 全局上限（默认 1000 条或 90 天），超出按「最老的非活跃」退休并留 `retiredReason` | 让写放大有上界 |

**P0 验收**：见 §七 的 1–6 条。**代价**：合并/节流会让个别过程信息晚到；退休会让默认视图看不到很老的任务（必须可查）。

### P1 · 降噪（不改格式，但改投递形态）

- **P1-1 合并窗口**：未消费通知按 `taskId` 合并（1–2 秒），直通类不参与；
- **P1-2 事实与投影分离**：报告正文只进账本，会话里发「摘要 + 指针」，把上下文占用从 O(正文) 降到 O(摘要)；
- **P1-3 自检**：`selfCheck` 增加 `memory` 块（账本条数、退休数、待读数、当前窗口、注入预算）。

**P1 验收**：同一任务一次派发产生的会话消息 ≤ 3 条；重复 id 计数为 0。

### P2 · 结构（需要改存储）

- **P2-1 写放大治理**：账本分片或追加式，替代整表重写（要带版本号与迁移）；
- **P2-2 per-lineage 预算**：worker 子树的注入量上限；
- **P2-3 退役审计视图**：看板增加「已退休」入口，回答「它什么时候、为什么消失的」。

---

## 七、验收清单（每条配可观测信号）

1. **消息条数**：一次派发 + 一次收尾，在会话里新增的插件来源 `user/message` ≤ 3 条；`progress` 默认 0 条。
2. **不重复**：同一任务 60 秒内未消费通知 ≤ 1 条；重复 message id 计数 = 0。
3. **不再投票**：归档/退休任务不进入成功率、中位耗时、并行节省；看板显示当前窗口。
4. **有上界**：`tasks.json` 条数 ≤ cap；每条退休记录带 `retiredAt` 与 `retiredReason`。
5. **不残留**：会话关闭后 `targets` 不新增孤儿条目；`inputPendingAt` 超 TTL 后变为 `unknown` 而非永久 pending。
6. **自检一致**：`selfCheck.memory` 的五个数与账本实际值一致（可脚本对账）。
7. **守恒**：账本 + 会话投影 + 退休记录 = 全量事实，且不重复计数。
8. **不变量**：会话事件总数单调不减（治理不含"删历史"语义）。

---

## 八、明确不做

- 不引入向量库 / 摘要模型 / 第二个存储器；
- 不新建 `ctx.<key>` 服务，不改 Session 格式代际；
- 不给模型加 `remember` / `forget` 工具，不让模型自己决定记什么；
- 不改 agent loop，不新增会话事件类型；
- 不做「把长期记忆和短期记忆拆成两个物理会话」——dsh 里只有一条只追加日志，分层是**投影策略**，不是存储分层。

---

## 九、风险与回滚

| 风险 | 应对 |
|---|---|
| 合并导致延迟 | 直通类（阻塞、失败、提问、批次汇总）永不参与合并；合并窗口上限 2 秒 |
| 退休等于静默丢历史 | 必须留 `retiredAt` / `retiredReason`，且可从 `dispatch_inspect` 与看板查到 |
| 指标数字跳变 | 窗口与口径显示在卡片 hover；切换窗口时提示「只统计最近 N 天」 |
| 文档再次漂移 | 先改 `docs/architecture.md` 的权威源口径，再改代码；本轮 0.8.x 的教训是文档说「辅助信息」而实际是权威源 |
| 一次性改太多 | 按 P0 → P1 → P2 分批；每批都要能单独回退（配置开关 + 默认值） |

---

## 十、落地顺序

1. 先把 §二 的口径冲突写进 `docs/architecture.md`（权威源定义），再动代码；
2. P0 五项一次发布，配套 `selfCheck.memory` 与 §七 的 1–6 条断言；
3. P1 在 P0 观察两周后做，重点看「消息条数」与「重复 id」两个信号；
4. P2 只在 P0/P1 仍不够时做——它会改文件格式，代价最高。
5. 与 [08 会话复用](08-session-reuse.md) 的关系：复用会把前序历史整段带进新任务，是污染的放大器，
   所以**先做完 P0 再谈复用**；「何时退休一整条线程」并入本文的 G4，别在两处各定义一套生命周期。
