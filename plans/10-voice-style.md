# 10 · 主会话的语言风格规划：先认领任务、再说人话、能一眼看懂

> **硬性要求（优先于“简短”）**：**每条与派发任务相关的回复**，第一句先说是**哪条任务**（短标题，不用 id），再说结论；批次里没成的任务必须逐个点名。纯问答不适用。
> 这条不是建议——派发多个任务后，报告回来时用户无法从状态或摘要反推是哪一条。

> 问题：派发回来的报告是机器写的（`[dispatch] 任务 t-1a9f-1 · 重构 auth · 报告 done`），
> 主会话把这段技术流水转述给用户时，常常变成「一堆状态 + 一串 id + 大段摘要」。
> 用户要的是「成没成、要不要我管、下一步做什么」，不是任务日志。
>
> 结论：**风格问题不能只靠一句「请简洁」。** 要同时改三处：
> ① 报告文本本身先变成「人话素材」；② 主会话提示里加一段固定的说话规则与篇幅预算；
> ③ 用可检查的文案契约把「先认领任务、不报 id、不报英文状态、先给结论」钉住。
> 本文只定风格与规则，不展开实现。

---

## 一、目标与非目标

### 目标

1. **先认领任务**：涉及派发任务的回复，第一句先说「这是哪条任务」，用短标题，不用 id；**即使只有一条也要说**——派发多了以后，用户不知道回来的是哪一条。纯问答不强行加任务名。
2. **一眼能判断**：说完任务名，立刻回答「成了没有 / 要不要我处理」。
3. **默认更短**：单任务默认 1–3 行，批次默认 1 行结论 + 最多 3 条要点。
4. **说人话**：不出现任务 id、子会话 id、`done/failed/blocked` 这类内部词；任务名用用户认得的标题。
5. **可展开**：用户要细节时能马上给，不靠记忆，靠账本。
6. **不撒谎**：没做成就是没做成；跑完但没结论，也要说清「它跑完了，但没给结论」。

### 非目标

- 不把主会话变成客服话术，不加「您好」「很高兴为您服务」。
- 不为简短牺牲准确性；失败、风险、需要决策的信息一条都不能省。
- 不追求统一的固定模板句；模板只用于兜底，不用于覆盖模型自己的表达。
- 不改看板与工具的既有文案体系（看板仍可显示状态词，因为它面向操作者）。

## 二、现在的风格问题（代码位置）

| 问题 | 现状 | 后果 |
|---|---|---|
| **回来不知道是哪条** | 派发多个任务后，报告只写状态与摘要，首句没有任务名 | 用户要自己从标题/摘要里猜，任务一多就对不上 |
| 报告首行是机器格式 | `reportText()`：`[dispatch] 任务 <id> · <标题> · 报告 <status>` | 主会话容易照抄，用户看到 id 与英文状态 |
| 内外信息混杂 | 报告里同时有任务 id、worker 会话 id、6000 字摘要、4000 字详情 | 主会话难以判断哪句才是重点 |
| 批次汇总是状态清单 | `done 3 / failed 1` + 每条一行 | 用户要自己数、自己归类 |
| 失败文案偏工程 | `启动失败：<error>` | 用户不知道「我现在该做什么」 |
| 提示词只讲机制 | `BACKGROUND_CONTRACT` / `HANDOFF_RULE` 很长，但没有「怎么对用户说」 | 模型行为正确，表达仍像日志 |
| 长提示词的稀释效应 | 规则越多，风格条款越容易被忽略 | 只加一句「请简洁」几乎无效 |

## 三、核心原则：先认领任务，再给结论

```text
任务 + 结论（哪一条 + 成没成 / 要不要你管）  ← 第一句同时回答「这是哪条」和「怎么样」
影响或原因（一句话）                         ← 只给会改变判断的那一条
下一步（可选，一句话）                       ← 有建议才写，没有就不写
```

**任务名写在第一句里，不单独占一行。** 例如「auth 令牌刷新那条修好了」，而不是先空一行写「任务：auth 令牌刷新」，再写结论——后者会把 2 行的预算撑成 3 行。

**任务名不是 id。** 用派发时的标题（或 6–12 字短标签），因为用户认得标题、不认得 `t-1a9f-1`。

**默认只写前两段。** 第三段只在「需要用户决策 / 建议重试 / 有风险」时出现。
细节不进入正文，统一留一个入口：`细节：dispatch_inspect t-xxxx`（仅当用户可能要追）。

### 篇幅预算

| 场景 | 默认上限 | 必须包含 |
|---|---|---|
| 单任务完成 | 2 行 | **任务短标签** + 做成了什么 |
| 单任务失败/阻塞 | 3–4 行 | **任务短标签** + 卡在哪 + 需要你做什么 |
| 多任务批次 | 1 行结论 + 最多 3 条 | **批次短标签** + 成了几条、没成的哪条、为什么 |
| 纯问答 | ≤3 句 | 直接答案 |
| 用户明确要细节 | 不受上限，但分段 | **任务短标签** + 结论仍在最前 |

### 任务短标签怎么起

1. 从任务标题取 6–12 字，优先保留「对象 + 动作」：`登录超时修复`、`CI 缓存迁移`、`结算接口测试`。
2. 去掉版本号、编号、括号补充、批次前缀；不要把 `07-P0`、`g-7f21` 这类内部编号当标签。
3. **同名任务必须区分**：用工作区或范围补一句，例如「结算服务那条『补集成测试』」「第二次跑的 auth 重构」。
4. 标签在一次回复里保持一致；不要同一任务前半句叫「登录超时」、后半句叫「auth 那条」。
5. 标题过长时宁可缩短，也不要退回 id；用户问 id 时再单独给。
6. **每条回来都要重新认领**：不能因为上一句提过就省略任务名；用户可能同时在盯多个会话，也不一定记得上一句说的是哪条。

### 禁止词与替换表

| 内部说法 | 对用户说 |
|---|---|
| `done` | 做完了 |
| `ended` | 跑完了，但它没给结论 |
| `failed` | 没做成 |
| `blocked` | 卡住了，需要你… |
| `interrupted` | 中途断了（宿主重启或会话被关） |
| `cancelled` | 已取消 |
| `queued` | 排队中 |
| `running` | 正在做 |
| `background` | 主流程结束了，后台还有活 |
| `dispatch_launch` / `dispatch_report` | 派给后台 / 汇报（除非用户在问工具本身） |
| 任务 id、子会话 id | 默认不出现；改用任务短标签；用户追问 id 时单独一行给 |
| `任务 A` / `第 1 条` / `刚才那个` | 用任务短标签；序号和“刚才”都不足以让用户认出来 |

**保留例外**：用户明确问「哪个任务」「id 是多少」「给我原始报告」时，照给，且不要偷偷省略。

## 四、报告文本要先像人话（给主会话的输入）

主会话很难把一段机器日志转述得自然；输入本身要先可读。

### 1. `dispatch_report` 增加一个可选 `headline`

- 定义：**一句话，给用户看的结论**，≤40 字，不含 id、不含英文状态、不重复任务名（任务名由外层「任务」行负责）；
- `summary` 保持技术摘要（做了什么、改了哪些文件、如何验证、遗留风险）；
- `detail` 保持长详情，只进账本与 `dispatch_inspect`；
- 缺 `headline` 时，系统用「标题 + 状态」生成兜底句，不能空着。

示例：

```text
headline: 已修好，补了 3 个回归测试
summary:  替换了 refresh 调用点 6 处；新增 3 条用例；pnpm test 全绿。
```

### 2. `reportText()` 的推荐形状

```text
【任务】auth 令牌刷新
【结果】登录超时修好了，补了 3 个回归测试
【说明】替换了 refresh 调用点 6 处；新增 3 条用例；测试全绿。
【需要你】无
【细节】dispatch_inspect t-1a9f-1
```

规则：

- **第一行必须是任务短标签**，让主会话知道这条属于哪个任务；第二行才是结论；
- 任务短标签从 `task.title` 生成/截短，不用 id；同名时加工作区或范围；
- `【需要你】` 只在 blocked / 失败 / 有决策时出现；
- 任务 id 只出现在末尾「细节」行；
- 摘要仍有长度上限，但**账本保留完整正文**，压缩只作用于「给模型看的那份」。

### 3. 批次汇总改成「结果分组」

现在：`done 3 / failed 1` + 四条一行一条。
建议：

```text
【批次】重构这批 4 条
4 条成了 3 条，1 条卡住。
· 成了：登录超时、接口重试、日志清理
· 卡住：补集成测试（连不上压测环境）
【需要你】把测试改成打本地 mock，还是你去开一下环境？
```

- 第一行先说**批次短标签**（用户当时怎么叫这批，就用那个名字），不要只写 group id；
- 先给比例，再给分组，不逐条复述成功项；
- **失败必须逐条点名到具体任务**（带短标签），不能只写「1 条失败」或「有 2 条没成」；
- 失败必须带原因与「需要你做什么」；
- 超过 5 条时只列「成了几条 / 没成的哪条」，其余让用户查。

### 4. 失败与中断的文案

都要带任务短标签，不能只报状态：

- 启动失败：`<任务短标签>：没能开始——<原因>`（不是 `启动失败：Error: ...`）；
- 中途断了：`<任务短标签>：中途断了，原因看起来是宿主重启；要我重试吗？`；
- 跑完无输出：`<任务短标签>：它跑完了，但没给结论——要我追问一句吗？`，**不要**写「本轮没有输出」这种机器句；
- 超时/卡住：`<任务短标签>：已经 8 分钟没动静，可能卡在 <最后一步>；要我看一下还是直接重试？`

## 五、主会话提示词里加一段「说话方式」

位置：现有 `BACKGROUND_CONTRACT` 之后、`HANDOFF_RULE` 之前（先讲机制，再讲表达，最后讲职责）。

控制在 **8 行以内**，避免把已经很长的提示词继续拉长；必要时删掉重复解释来腾位置。

```text
说话方式（对用户，不是对系统）:
- 先认领再结论：每条回来都先说「哪条任务」（短标题，不用 id），再说成没成 / 要不要你管；只有一条也要说。
- 默认 2-3 行；多任务先说批次短标签与比例，再最多列 3 条，没成的必须点名。
- 说人话：不报任务 id、子会话 id、done/failed/blocked 这类内部词；用户问起再给。
- 不写过程流水账，不复述用户的问题，不说「报告已回流」。
- 失败必须说清「卡在哪 + 你只需要做什么」；不确定就说不知道。
- 有下一步建议才写，没有就不写；不要用「如需…请告诉我」凑结尾。
- 用户要细节时再展开，细节从 dispatch_inspect 取，不要凭记忆编。
```

**优先级写明**：风格规则不得覆盖事实与安全规则；当简洁与准确冲突时，先准确。

## 六、示例：改前 / 改后

### 例 1 · 单任务完成

改前：

```text
[dispatch] 任务 t-1a9f-1 · 重构 auth 模块的令牌刷新 · 报告 done
摘要：替换 refresh 调用点 6 处，剩余 2 处在 webhook 模块……（略）
```

改后：

```text
auth 令牌刷新那条：登录超时修好了，补了 3 个回归测试，测试全绿。
还有 2 处 webhook 的调用点没动，要不要一起收掉？
```

### 例 2 · 批次里有失败

改前：

```text
[dispatch] 批次 g-7f21 全部结束（4 个任务：done 3 / failed 1）
- 重构 auth · done：已替换 6 处
- 重构 billing · done：幂等键统一
- 重构 notify · done：模板渲染完成
- 补集成测试 · failed：压测环境连不上
```

改后：

```text
重构这批 4 条：成了 3 条，1 条卡住——「补集成测试」连不上压测环境。
代码改动的 3 条都好了；要我把测试改成打本地 mock，还是你去开一下环境？
```

### 例 3 · 阻塞需要决策

改前：

```text
任务 t-2b3c-2 报告 blocked：需要 GitHub 组织级 token 才能改 cache 权限
```

改后：

```text
「CI 缓存」这条卡住了：改 cache 权限要组织级 token。
你给我 token，或者我改成仓库级缓存（效果差一点但今天能完成）——选哪个？
```

### 例 4 · 同名任务要能区分

```text
结算服务那条「补集成测试」没做成：压测环境连不上。
dsh-mini-superagent 那条同名任务已经跑完了，测试全绿。
```

不写「第 1 条成功、第 2 条失败」——用户要回头对账时，序号帮不上忙。

## 七、怎么验证「真的更懂了」

模型输出不可用单测完全约束，所以分两层：

### 1. 文案契约（可自动检查）

- **任务相关回复的首句必须包含任务短标签**（来自 `task.title`，不是 id）；只有一条任务时也要有；纯问答例外；
- `reportText` 首行（`【任务】`）与主会话首句的任务名必须一致；
- `reportText` 首行不含 `t-` 开头的 task id、不含 `done|failed|blocked|ended|interrupted`；
- 任务名行长度 ≤ 40 字，整个首句 ≤ 60 字；
- 失败/阻塞报告必须包含「需要」或「要你」这类行动指向；
- 批次汇总必须包含「批次短标签 + 成了/没成」的计数，且**没成的任务必须点名**；
- 风格提示段 ≤ 8 行、≤ 500 字，防止提示词继续膨胀；
- 账本原始 `summary` / `detail` 不被压缩（只压缩投影）。

### 2. 人工盲评（每轮改文案后跑一次）

固定 10 个场景（单条完成、单条失败、批次全成、批次有失败、阻塞、超时、中断、纯问答、用户要细节、无输出）：

- 每段回答只给 10 秒阅读时间；
- 评四项：**能否马上知道是哪条任务 / 能否一眼判断结果 / 是否知道下一步 / 是否觉得啰嗦**（1–5 分）；
- 通过线：前三项平均 ≥4，「啰嗦」反向评分 ≤2；
- 任一条出现「不知道说的是哪条」或「看不懂」即打回，不以平均分掩盖。

### 3. 回归方式

把 10 个场景的输入与理想回答存成 `docs/voice-samples.md`（只存样例，不做自动模型断言）；
每次改提示词或报告模板，人工对照重跑，避免「越改越像机器」。

## 八、分期

| 阶段 | 做什么 | 验收 |
|---|---|---|
| P0 · 文案先人话 | `headline` 字段（可选）；`reportText` 改成「任务 + 四段式」；失败/中断文案改写；批次汇总分组并点名失败项 | 文案契约 8 条全过；旧报告仍能兜底显示 |
| P1 · 提示词定调 | 加 8 行「说话方式」（先认领任务）；给 1–2 组改前/改后示例进提示；控制提示长度 | 人工盲评 10 场景通过（含「知道是哪条任务」） |
| P2 · 默认短、按需长 | 主会话默认 2–3 行；`dispatch_inspect` 返回「可直接转述的详情」；用户说「展开」时给全 | 用户不需要学命令就能拿到细节 |
| P3 · 校准 | 按真实对话回收「哪句最常被追问」；只调文案，不动机制 | 追问率下降，且没有漏报失败 |

## 九、风险与边界

| 风险 | 应对 |
|---|---|
| 过度简短导致漏报失败/风险 | 失败、阻塞、风险三类信息**永不压缩**；压缩只作用于过程与重复标题 |
| 任务名太长，把首句撑爆 | 用 6–12 字短标签；标题里的版本号、批次号、括号补充全部剥掉 |
| 同名任务认错 | 标签后补工作区或范围（「结算服务那条『补集成测试』」）；禁止用序号代替 |
| 多任务只报比例、不点名 | 批次汇总必须点名没成的任务；成功项可合并 |
| 模板句让模型说话更僵 | 模板只给「兜底句」，正文让模型自己组织；示例只放一组 |
| 提示词继续膨胀 | 风格段 ≤8 行；新增内容前先删一段重复解释 |
| 用户要 id / 原始报告 | 明确例外：问就给，不省略，不装作没有 |
| 多模型表现不一致 | 用文案契约兜住「任务名、首行、禁止词、行动指向」，不依赖某个模型自觉 |
| 风格与事实冲突 | 优先级写明：准确 > 简洁；不确定必须说不知道 |

## 十、一句话总结

**先说哪条，再说成没成，最后说要不要你管。**
报告先像人话，主会话才说得出人话；提示词只负责定调，文案契约负责兜底。
细节留在账本，不堆在嘴上。
